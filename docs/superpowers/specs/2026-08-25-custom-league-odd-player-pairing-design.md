# Custom League Odd-Player Dynamic Pairing — Design

**Date:** 2026-08-25
**Status:** Approved for planning

## Problem

Custom League uses fixed, organizer-defined team pairs (set up on the Teams page via manual "Pair" or "Shuffle Remaining Players"). When the tournament's total player count is odd, one player always lands in "Unpaired players" and is **never placed on any team** — so they never enter `computeCustomAutoRound`'s pool and cannot play a single match for the entire tournament. This is upstream of, and separate from, `computeCustomAutoRound`'s existing (correct) team-level sit-out rotation, which only kicks in once a *team* count is odd — it has no way to help a player who was never assigned a team at all.

Because Custom League allows public sign-up mid-tournament (the shareable league link), the total player count can flip between even and odd between rounds — this is not a one-time setup condition.

## Scope decisions (resolved during brainstorming)

- **Fixed teams are preserved for the even case.** When the tournament's current total player count is even, everything works exactly as it does today: organizer-defined fixed teams, `computeCustomAutoRound`'s team-level fairness rotation. This code path is not modified.
- **Dynamic (per-round, individual-player) pairing kicks in only for rounds generated while the total player count is odd.** This is re-evaluated every time a round is generated — not stored as a tournament-level flag — so a tournament can use fixed teams for round 1 (even) and dynamic pairing for round 2 (odd, after a new sign-up), and back again.
- **Manual match management stays available in odd mode.** The organizer can still add a match by hand for an odd round; the form picks 4 individual players instead of 2 existing teams.
- **Fairness must hold across mode switches.** A player whose fixed team sat out in an even round must have that sit-out counted the next time an odd round's dynamic pairing decides who sits out — otherwise the exact problem being fixed could resurface in a different shape. This is solved with a shared, derived player-level history (see Architecture) rather than two disconnected fairness ledgers.
- **`computeCustomAutoRound` (the existing even-round/fixed-team generator) is not modified.** Its own team-level rotation already works correctly for the rounds it generates; it does not need to read the new player-level history to keep doing so.

## Architecture

Two new pure, unit-tested modules, following the codebase's existing pattern (`customAuto.ts`, `popcorn.ts`, `gauntlet.ts`):

### `lib/tournament/customPlayerHistory.ts`

```ts
export type PlayerHistory = {
  sitOutCounts: Map<string, number>;   // playerId -> rounds sat out
  partnerCounts: Map<string, number>;  // pairKey(p1, p2) -> times they were teammates
  opponentCounts: Map<string, number>; // pairKey(p1, p2) -> times they were on opposite teams
  lastMetRound: Map<string, number>;   // pairKey(p1, p2) -> most recent round they shared a court (partner or opponent)
};

// Derives player-level fairness history purely from match history -- covers rounds
// generated by EITHER the fixed-team (even) generator or the dynamic (odd) generator
// identically, by expanding each match's two teams into their four constituent players.
// This is what keeps fairness consistent across mode switches: a team's sit-out in an
// even round becomes its two players' sit-out here, exactly as if they'd sat out
// individually.
export function derivePlayerHistory(
  playerIds: string[],
  matches: { round: number; teamAId: string; teamBId: string }[],
  teams: { id: string; player1Id: string; player2Id: string }[],
  beforeRound: number // only rounds strictly before this are considered
): PlayerHistory;
```

For each round strictly before `beforeRound` that has at least one match: expand every match's `teamAId`/`teamBId` into player pairs via `teams`, mark those four players as having played that round (everyone else in `playerIds` sat out), record the two within-team pairs as partners and the four cross-team pairs as opponents for that round.

### `lib/tournament/customDynamic.ts`

```ts
export type CustomDynamicPairing = {
  teamAPlayerIds: [string, string];
  teamBPlayerIds: [string, string];
};

// Computes one round's pairings from a live player-history snapshot. Throws if fewer
// than 4 players are supplied (same floor as generateGauntletRound / generatePopcornSchedule
// -- a match needs 4 players). Sits out playerIds.length % 4 players (fewest sit-outs
// first, ties broken by input order -- deterministic, no randomness, matching
// computeCustomAutoRound's convention), then groups the rest into foursomes and splits
// each into two teams, minimizing repeat partners and (secondarily) repeat opponents,
// using the same grouping approach as popcorn.ts's per-round logic. This is a fresh
// implementation, not a refactor of popcorn.ts -- touching already-shipped, tested code
// for an unrelated format is a bigger risk than the small amount of duplicated shape.
export function computeCustomDynamicRound(
  playerIds: string[],
  history: PlayerHistory
): CustomDynamicPairing[];
```

## Wiring into `bracket/actions.ts`

### `autoGenerateCustomRound`

After computing `nextRound` (unchanged: `max(existing rounds) + 1`), fetch the tournament's current `players` and check `players.length % 2`:
- **Even:** existing path, unchanged — `computeCustomAutoRound(teams, existingMatches, nextRound)`.
- **Odd:** fetch `teams` (needed to expand matches to players) and this tournament's full match history, call `derivePlayerHistory(playerIds, matches, teams, nextRound)`, then `computeCustomDynamicRound(playerIds, history)`. For each resulting pairing, look up or create an ad-hoc team for each player pair using the same `pairKey`-based lookup-or-create pattern `generatePopcornBracket`/`advanceGauntletRound` already use in this file (no new team-storage concept). Insert the resulting matches with `stage: 'league', round: nextRound`, courts assigned via the existing `assignCourts` (plain, not `assignCourtsByRound` — this call always generates exactly one round, same as the gauntlet/custom-auto call sites already do).

### `addCustomMatch`

Add the same even/odd check (current total player count). In odd mode, read 4 distinct player IDs from the form instead of 2 team IDs, validate all 4 belong to the tournament and none is already in a match for the target `round` (double-booking check), look up or create the two ad-hoc teams via the same `pairKey` pattern, then insert exactly as today (including the existing per-round court index computation, unchanged).

### Bracket page ("Add match" form)

The form conditionally renders: 2 team-select dropdowns (even mode, today's behavior) or 4 player-select dropdowns grouped as "Team A" / "Team B" (odd mode). Which mode to render is decided server-side from the tournament's current live player count when the page renders, same as other format-conditional UI already on this page.

### Teams page

No structural change — it already unconditionally lists whatever's in the `teams` table, fixed or ad-hoc alike. Add one contextual note, shown only when the live player count is currently odd, near the "Unpaired players" section: the extra player will be woven into matches automatically the next time a round is generated, rather than sitting out permanently. Any player already stuck in "Unpaired players" before this ships starts getting included automatically the next time a round is generated — dynamic mode reads directly from the full player list, not from `teams`, so there's nothing to migrate.

## Testing

- `lib/tournament/customPlayerHistory.test.ts` (new): `derivePlayerHistory` — zero history (all counts start at 0), a single even-generated round correctly expands team sit-outs/pairings to their players, a mix of matches from different rounds accumulates correctly, `beforeRound` correctly excludes matches at or after the cutoff.
- `lib/tournament/customDynamic.test.ts` (new): `computeCustomDynamicRound` — throws under 4 players, sits out exactly `n % 4` players prioritizing fewest-sit-out players first, deterministic tie-breaking (no randomness), groups avoid repeat partners when history allows, falls back to least-recently-met when repeats are unavoidable.
- `computeCustomAutoRound`'s existing tests (`customAuto.test.ts`) are untouched — that function's behavior does not change.
- `bracket/actions.ts` and `bracket/page.tsx` have zero test coverage anywhere in this codebase, by established convention (confirmed in the prior court-assignment feature's plan) — the mode-selection wiring in `autoGenerateCustomRound`, `addCustomMatch`, and the bracket page form is verified via `npm run build` (typecheck) + `npm test` (regression) only, plus manual verification in the running app.

## Migration

None required. Ad-hoc teams reuse the existing `teams` table schema (`player_1_id`, `player_2_id`) exactly as Popcorn/Gauntlet already do — no new columns or tables.

## Out of scope

- Refactoring `popcorn.ts` to share its grouping logic with `customDynamic.ts` (noted as a possible future DRY cleanup, not required now).
- Any UI to let the organizer manually force dynamic mode while player count is even, or force fixed-team mode while odd.
- Changing `computeCustomAutoRound`'s own algorithm or test suite.
